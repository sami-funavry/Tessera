# Deterministic fix plan — post-P-10.11 live findings

> Generated 2026-05-09 after live UI testing surfaced 7 bugs.
> Output of three parallel investigation agents + manual code tracing.
> **No code is changed by this document.** It is the plan the operator approves before any of these land.
> Order of fix is calibrated to "land critical-path first, telemetry/UX last," and every fix has a determinism check so we don't re-introduce the bug.

---

## TL;DR — what's broken right now

Three of these are critical-path (every Neutron→Sepolia user-bridge runs into them); two are demo-day annoyances; two are telemetry/UX.

| ID | Severity | Symptom | Root cause |
|---|---|---|---|
| **B-1** | P0 | Neutron→Sepolia user bridge reverts on Sepolia (`UnknownNonce`); UI stuck at "Submitted" | Frontend routes `destination_app = bridgeVault`; should be `bridgeMint` (see P-10.10d for the same fix on the admin path) |
| **B-2** | P0 | Dashboard shows 2 rows per Neutron→Sepolia bridge (e.g. `#216` finalized + `#215` pending, same source tx) | Frontend nonce `BigInt(Date.now())` vs relayer nonce `binary.BigEndian.Uint64(tx.Hash[:8])` — different values → upsert key `(source_chain_id, nonce)` doesn't dedupe |

| **B-5** | P2 | "Avg bridge time" on dashboard | Already real (live computation over executed `messages.updated_at - created_at`). Documented imprecision: `created_at` may be either intent-time or detection-time. No code fix; clarify the metric definition |
| **B-6** | P1 | Benchmark "Destination gas" stuck on `—` | No write path exists. Schema has `submissions.dest_gas_used` and `benchmark_runs` but nothing in the relayer writes either |

Compounded by the misunderstanding that trigger-burn moves the OPPOSITE chain's balance |

## B-1 — Neutron→Sepolia destination revert (P0, blocks demo)

### What happens
1. User clicks "Bridge" with Neutron→Sepolia direction in the widget.
2. `frontend/app/HomepageClient.tsx:1466-1478` calls `cosmWasmClient.execute` on bridge-mint with `destination_app: ADDRESSES.sepolia.bridgeVault` (`0x23d1a91A…0603Ce`).
3. Relayer detects the burn, builds payload, submits proof to Sepolia Verifier.
4. After the 60s window, relayer calls `Verifier.executeMessage`.
5. Verifier abi-decodes `destinationApp` as `address` and dispatches to `BridgeVault.onCrossChainMessage`.
6. `BridgeVault.release` reverts at `contracts-evm/src/BridgeVault.sol:110` with `UnknownNonce(nonce)` — `lockedAmount[nonce] == 0` because the burn nonce was never used to lock anything on Sepolia.
7. Tx fails on-chain (Status=0). Confirmed live on `0x8200d0a6...0a01`.

### Root cause
For a Neutron-source user bridge the user is depositing tokens to be **received** on Sepolia. That means tokens are **minted fresh** by `BridgeMint.bridgeMintTo`, not released from a lock that doesn't exist. The admin path already fixed this in P-10.10d (`relayer/internal/relayer/admin.go:108-122`); the user path missed the same correction.

### Fix
**File:** `frontend/app/HomepageClient.tsx`
**Edit:** in the Neutron→Sepolia burn block (around line 1473), change
```ts
destination_app: ADDRESSES.sepolia.bridgeVault,
```
to
```ts
destination_app: ADDRESSES.sepolia.bridgeMint,
```

**Defense in depth (optional, recommended):**
**File:** `relayer/plugins/tendermint/plugin.go:332`
**Edit:** change the fallback from `p.addrs.SepoliaBridgeVault` to `p.addrs.SepoliaBridgeMint` so that any future caller who forgets the explicit destination_app gets the safe default. This matches the admin-path convention.

### Determinism check
`BridgeMint.onCrossChainMessage` (`BridgeMint.sol:62-72`) calls `tusdc.bridgeMintTo(recipient, amount)` with no nonce-state precondition; payloads with valid `(address, uint256, uint64)` shape always succeed. Add a Foundry test asserting `Verifier.executeMessage` succeeds for `destApp = BridgeMint` and reverts `UnknownNonce` for `destApp = BridgeVault` on a never-locked nonce — pins the regression.

### Risk
- Sepolia→Neutron user flow: unaffected (destApp is `neutron-bridge-mint`, no change).
- Sepolia→Neutron→Sepolia round-trip with a known prior lock: this would NEED `bridgeVault`. Not exercised by the demo; the admin override `dest_app=` query param remains for future use.
- All four scenarios (S-1 honest, S-2 lying, S-3 silent, S-4 frivolous): unaffected since they're Sepolia-source.

### Re-test
1. From the live UI, connect Keplr + MetaMask, bridge 1 tUSDC Neutron→Sepolia.
2. Verify the burn tx hits bridge-mint successfully on Neutron.
3. Verify the relayer's submit + execute on Sepolia returns Status=1 (Etherscan).
4. Verify recipient's Sepolia tUSDC balance increased by exactly 1e18 (10^12 scaling × 1e6 base units).

## B-2 — Duplicate dashboard rows (P0 for trackability, not blocks demo)

### What happens
Two writers race for the same source tx:
- `frontend/app/api/bridge/relay/route.ts:122-142` inserts a row with `nonce = BigInt(Date.now())` (frontend's recordIntent).
- `relayer/plugins/tendermint/plugin.go:307` later upserts a row with `nonce = binary.BigEndian.Uint64(tx.Hash[:8])`.

Different nonces → upsert key `(source_chain_id, nonce)` (per `relayer/internal/supabase/client.go:148`) doesn't collide → two rows. The relayer's row gets the executed update; the frontend's row sticks at `pending` forever.

The frontend has an idempotency check on `source_tx_hash` (`route.ts:104-117`), but it only fires if the relayer wrote first. In practice the frontend always wins because relay polling is on a 10s tick and recordIntent is called within seconds of the user signing.

Sepolia→Neutron is unaffected because Sepolia's `BridgeVault.lock` takes the nonce as a caller argument; the frontend supplies it, the relayer reads it from the Locked event — they always match.

### Root cause
Bidirectional asymmetry: Sepolia event preserves the frontend-supplied nonce; Neutron event derives nonce from tx hash, which the frontend can't predict at signing time.

### Fix (Option A — minimal, recommended)
**File:** `frontend/app/HomepageClient.tsx`
**Edit:** in the Neutron→Sepolia path (after `cosmWasmClient.execute` returns):
```ts
const burnRes = await cosmWasmClient.execute(...);
// Mirror the relayer's nonce derivation: first 8 bytes of the tx hash, big-endian.
// Same formula as relayer/plugins/tendermint/plugin.go:307 → both writers
// produce identical nonces and the (chain_id, nonce) upsert dedupes.
const txHashHex = burnRes.transactionHash.replace(/^0x/i, '').toLowerCase();
const sharedNonce = BigInt('0x' + txHashHex.slice(0, 16));
setTxNonce(sharedNonce);
// ...recordIntent({ ..., nonce: Number(sharedNonce) });
```

The Sepolia→Neutron path can keep its current `BigInt(Date.now())` nonce — that nonce IS the on-chain nonce (passed to `BridgeVault.lock`).

### Fix (Option B — robust, more work)
Switch the `messages` table's upsert key to `(source_chain_id, source_tx_hash)`. Cleaner conceptually (the source tx is the natural key) but requires a Supabase migration AND a `relayer/internal/supabase/client.go` change. Defer to post-hackathon unless the Option-A fix has subtle issues.

### Determinism check
The relayer's `binary.BigEndian.Uint64(tx.Hash[:8])` and the frontend's `BigInt('0x' + hex.slice(0,16))` are bit-identical big-endian reads of the same 32-byte hash. Add a tiny unit test pinning the hex parsing (e.g. for a known fixture hash, both sides produce the same uint64).

### Risk
- Sepolia→Neutron path uses the existing nonce derivation (`Date.now()`) — no change.
- Neutron→Sepolia path now generates a deterministic nonce from the tx hash — collision probability is negligible (uint64 over a small set of bridges per day).
- A future Neutron-source bridge could theoretically race itself by submitting two burns within the same block... unlikely, and even then the user gets the relayer's row, not a duplicate.

### Re-test
After the fix, do another Neutron→Sepolia user bridge. Dashboard should show exactly ONE row. Realtime subscription should update to executed.

## B-3 — Status = FINALIZED despite reverted destination tx (P0 for observability)

### What happens
1. `relayer/internal/relayer/submitter.go:272` calls `ps.DestPlugin.ExecuteMessage(ctx, ...)`.
2. EVM `ExecuteMessage` (`relayer/plugins/ethereum/plugin.go:501-516`) calls `sendTx`, which only broadcasts (the comment at line 748 says "does not wait for confirmation").
3. `ExecuteMessage` returns the broadcast hash with `nil` error.
4. `submitter.go:286` writes `dbUpdateMessageStatus(ctx, ps.MessageDBID, "executed")`.
5. The destination tx later reverts (Status=0). Nothing reads the receipt; nothing updates the row.

Result: dashboard shows `FINALIZED` with a destination tx hash that's actually a revert.

### Root cause
`ExecuteMessage` lacks the receipt-status check that `SubmitMessage` already has (`SubmitMessage` calls `waitForSubmissionID` which does check `receipt.Status == 0` per the F-105 audit fix at `ethereum/plugin.go:826-829`).

### Fix
**File:** `relayer/plugins/ethereum/plugin.go::ExecuteMessage` (around line 501)
**Edit:** after `sendTx` returns the hash, call the existing `waitForReceipt` helper (line 722) and check `receipt.Status`. Return the existing `ErrTxReverted` (line 798) on revert.
```go
txHash, err := p.sendTx(ctx, p.addrs.SepoliaVerifier, data, nil)
if err != nil { return "", fmt.Errorf("ethereum ExecuteMessage: %w", err) }

// Wait for the receipt and surface revert as an error.
status, _, err := p.waitForReceipt(ctx, txHash)
if err != nil { return "", fmt.Errorf("ethereum ExecuteMessage receipt: %w", err) }
if status == 0 { return "", fmt.Errorf("ethereum ExecuteMessage %w: tx %s", ErrTxReverted, txHash) }
return txHash, nil
```

**File:** `relayer/internal/relayer/submitter.go::scheduleExecuteMessage` (around line 272)
**Edit:** on `err != nil`, branch on `errors.Is(err, ethereum.ErrTxReverted)`. Write `dbUpdateMessageStatus(ctx, ps.MessageDBID, "reverted")` and `dbUpdateSubmissionStatus(ctx, ps.SubmissionDBID, "reverted", "")`. Emit a pipeline `Reverted` event so the demo log surfaces it.

The bridge widget already handles `row.status === 'reverted'` (`HomepageClient.tsx:1263-1267`), so the user-facing UX is already wired — it's just never reached today.

### Determinism check
`receipt.Status == 0` is the canonical EVM revert signal across all RPCs. Unit test: deploy a Verifier where dispatch always reverts, call `ExecuteMessage`, assert relayer writes `status=reverted`.

### Risk
- Adds a ~30-90s blocking wait inside `scheduleExecuteMessage`. The goroutine is per-message (`submitter.go:240-243`), so it doesn't block other relays.
- Honest scenarios (S-1) still complete normally because Status=1.
- S-2 (lying): execute is skipped because the submission was already slashed (`scheduleExecuteMessage:259-265` short-circuits). No regression.
- S-3 (silent): execute proceeds via the OTHER relayer; same Status=1 path. No regression.
- S-4 (frivolous): execute proceeds normally on the original honest submission. No regression.

### Re-test
After the fix, re-run the bridge with `destination_app = bridgeVault` (i.e. don't fix B-1 yet, OR apply B-1 and force a revert via a contract whose dispatch fails). Verify:
1. The destination tx shows Status=Fail on Etherscan.
2. The dashboard row goes to `REVERTED`, not `FINALIZED`.
3. The bridge widget surfaces a "transaction reverted" error to the user.

## B-4 — S-3 silent scenario shape (verification only, no code change)

### What happens
User saw lock + verify + transform events for `0x2501e4...dff9`, then nothing. No submit/window/execute followed.

### Why this is the correct shape
S-3 silences the submitter. The silenced relayer fires `Locked + ProofFetched + ProofTransformed` (lines 67-89 of `submitter.go`), then short-circuits at the `IsSilent` check before calling `SubmitMessage`. So no submit, no window, no execute from this relayer.

The expected continuation is on the OTHER relayer:
- Other relayer sees the same Locked event.
- Other relayer runs the full submit→window→execute pipeline.
- After `Deadline + 30s`, ANY relayer (including the silenced one, on a fresh start) calls `claimAbsenceSlash`.
- That fires `AbsenceSlash` in the events table (`challenger.go:219-227`).

If only ONE relayer is up and it's silenced: no successor → message permanently stuck. That's protocol-correct, not a bug.

### Verification approach
1. Confirm both `relayer-a-production.up.railway.app` and `relayer-b-production.up.railway.app` are alive (e.g. `/healthz` or first event-loop log line).
2. Use `/api/scenarios/silent` from the demo page (this primes ONE relayer).
3. Watch the OTHER relayer's logs for `handleEvent: message submitted` against the same source tx.
4. Confirm an `AbsenceSlash` row appears in `events` with `relayer = silenced relayer's address`.

### Action item
Add a small "S-3 verification" subsection to `docs/audit-findings.md` and to in-app `/docs` Demo Scenarios, explaining that the silent scenario log shape is by-design and what the operator should see on the OTHER relayer.

### Risk
None. No code change.

## B-5 — Avg bridge time accuracy (clarify, no fix)

### What happens
The dashboard "AVG. BRIDGE TIME" reads from `useBenchmarkStats` (`frontend/hooks/useBenchmarks.ts:117-129`), which:
1. Queries the last 100 `messages` with `status='executed'`.
2. Computes `updated_at - created_at` per row.
3. Averages.

This IS live. But:
- `created_at` defaults to Postgres `now()` at first insert, which is whichever writer wrote first (frontend's `recordIntent` after the user signs, OR the relayer's UPSERT after on-chain detection).
- `updated_at` is set to `now()` on each PATCH, including the final `status='executed'` write.

For Sepolia→Neutron: frontend writes first (within ~1s of user signing) → `created_at ≈ user-signing-time`. Avg therefore ≈ "time from user signing to execute on Neutron" ≈ ~85-95s (60s window + ~25s submit + ~5s execute).

For Neutron→Sepolia: same shape post-B-2 fix.

### Verdict
Live, real, directionally correct. No code fix.

### Action item
Clarify in `/docs` and Notion that the metric is "time from first DB write (intent or detection, whichever first) to executed status."

## B-6 — Destination gas always empty (P1 telemetry)

### What happens
- `frontend/app/benchmark/page.tsx:82` shows `—` because `useBenchmarkStats` returns `avgDestGas: null`.
- `useBenchmarks.ts:138` hardcodes null with comment "Gas data is not derivable from the messages table."
- The schema has `submissions.dest_gas_used bigint NULL` (`relayer/internal/supabase/client.go:107`) and a `benchmark_runs.dest_gas_used` field (line 99-109), but **neither is ever written**. `InsertBenchmarkRun` is defined and never called (grep-confirmed).

### Fix
**File:** `relayer/plugins/ethereum/plugin.go::ExecuteMessage` (paired with B-3's receipt wait)
**Edit:** return `(txHash string, gasUsed uint64, err error)` instead of `(txHash string, err error)`. Read `receipt.GasUsed` after the wait. Same shape on the Tendermint side using `result.TxResult.GasUsed`.

**File:** `relayer/internal/chain/plugin.go::Plugin` interface
**Edit:** signature change for `ExecuteMessage`.

**File:** `relayer/internal/relayer/submitter.go::scheduleExecuteMessage`
**Edit:** after success, write `r.cfg.DB.UpdateSubmissionDestGas(ctx, ps.SubmissionDBID, gasUsed)` (new method on `supabase.Client`).

**File:** `relayer/internal/supabase/client.go`
**Edit:** new method `UpdateSubmissionDestGas(id int64, gasUsed uint64) error` that PATCHes `submissions.dest_gas_used`.

**File:** `frontend/hooks/useBenchmarks.ts`
**Edit:** join `messages` with `submissions` on `message_id`, average `submissions.dest_gas_used` for executed rows. Replace the hardcoded `avgDestGas: null` with the live average.

### Determinism check
`receipt.GasUsed` (EVM) and `TxResult.GasUsed` (Cometbft) are exact post-execution values. After fix, S-1 honest run produces a non-null `submissions.dest_gas_used`; integration test asserts `avg(dest_gas_used) > 100_000` (sanity floor for `BridgeMint.bridgeMintTo`).

### Risk
- The signature change on `Plugin.ExecuteMessage` ripples to all plugins (currently 2: ethereum + tendermint). Both must be updated together.
- Frontend join query is a small Supabase query change; tests around `useBenchmarkStats` need updating.

## B-7 — Admin balances don't refresh after claim/burn (P1 UX)

### What happens
- `frontend/app/admin/page.tsx:249,285` does `setTimeout(() => refreshBalances(), 4000)`.
- 4s is too short for Sepolia (block time ~12s) and borderline for Neutron (block time ~2-3s).
- For trigger-burn specifically, the relayer's Sepolia tUSDC balance only changes after the FULL bridge completes (~90s), not after the burn alone.

User-claim handlers (`frontend/app/admin/page.tsx:151,175-181`) do the right thing: `await publicClient.waitForTransactionReceipt({ hash, timeout: 90_000 })` BEFORE refreshing. Relayer-claim and trigger-burn don't.

### Fix
**File:** `frontend/app/admin/page.tsx::relayerClaim`
**Edit:** after the admin proxy returns `data.tx_hash`, on Sepolia chain wait for `publicClient.waitForTransactionReceipt({ hash: data.tx_hash, timeout: 90_000 })`, then refresh. On Neutron, poll a CW query at 3s intervals until balance changes (or 30s timeout).

**File:** `frontend/app/admin/page.tsx::triggerBurn`
**Edit:** trigger-burn is a cross-chain bridge, so balance updates take ~90s on the destination side. Schedule polling at 5s intervals for 120s, refreshing on each tick. Show a subtle "Bridge in flight…" indicator under the trigger-burn button until the relayer's destination balance reads the expected delta.

### Determinism check
`waitForTransactionReceipt` returns once the tx is mined (single block). For trigger-burn, the destination balance change is bounded by `60s window + ~5s buffer + receipt time` ≈ 90s. 120s polling window catches >99% of healthy runs. If not seen, surface a "Bridge still in flight — check the dashboard" message.

### Risk
None to working paths. User-claim handlers are unchanged; only relayer-claim and trigger-burn handlers gain a real wait + indicator.

## Suggested fix order

1. **B-1** + **B-2** + **B-3** in a single PR — these are all in the critical path and they reinforce each other:
   - B-1 unblocks the transaction (no more revert).
   - B-2 makes the dashboard row trackable (no more orphan `pending`).
   - B-3 makes any future revert observable (no more silent FINALIZED).
   Estimated effort: ~2 hours including test runs.

2. **B-7** as a follow-up — pure frontend UX, no code paths beyond the admin page.

3. **B-6** as a third PR — touches `Plugin` interface; bigger blast radius.

4. **B-4 + B-5** as documentation patches in the same Notion + in-app docs sweep.
